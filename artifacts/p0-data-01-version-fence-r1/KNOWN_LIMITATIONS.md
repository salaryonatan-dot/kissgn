# KNOWN LIMITATIONS — R1 (recorded, not hidden)

1. **Client behaviour on control-record disappearance (Codex, NON-BLOCKING, not implemented in R1).** A client that observed `quiesced` at revision N and then sees the WHOLE record disappear falls back to the absent-record legacy decision (writable, revision sentinel 0). Server truth is unaffected: only whole-record absence is legacy on the server too, and NOTHING can delete a record except a privileged actor — Rules deny every client write/delete at every level of `storage_v2_control` (VF-10, A13-120…128), the tooling has no delete operation, and the only privileged deletion path (`delete-client`) is now maintenance-gated (a quiesced/held business blocks it). **Canary evidence requirement:** the canary runbook must assert that `storage_v2_control/{t}/{b}` exists for the canary business at every step and that no operator path deletes records. A client-history rule ("once quiesced, treat absence as `policy_rollback`") is a candidate follow-up, not part of R1.
2. **Old historical page display after activation** — unchanged (accepted): every write it emits is denied (now proven from a rendered page), its UI stays misleading; operational answer = reload/update.
3. **Admin bypasses Rules** — unchanged: "conversion only in quiesced", ownership and no-downgrade remain application-level invariants of `tools/storage-v2/policy.mjs`; runbooks must use the wrapper. Non-entries business documents (checklists via `setBizDocGuarded`) are not maintenance-gated — they are outside the entries domain the fence protects (inventory item 11).
4. **`api/admin.js` gates admission only** — a request admitted an instant before `quiesce` may still commit; in-flight server work is drained operationally.
5. **Transport at the numeric edge:** on the emulator, an SDK transaction on a node holding an integer ≥ 2^53−2 never commits (`maxretry`, client/server hash mismatch). Unreachable operationally (one increment per transition; `revision_exhausted` at MAX_SAFE_INTEGER refuses inside the callback without a server commit). Documented in `REVISION_BOUNDARY.md`.
6. **Rules read the phase of `operation.kind` structurally, not its relationship to `phase`** (a `recovery` operation on a `quiesced` record is VALID for Rules; the tooling never writes one). Not an exposure: the phase alone decides admission.
7. **Rows-map whole-deletion residual** from the core — unchanged.
8. **Rendered-page proof scope:** jsdom (no layout/paint); Firebase client SDK replaced by an API-identical shim over the Admin SDK with member auth override (the SDK wire path is covered by VF-26 and the fence matrix).
9. Pre-cutover blockers (out of scope): production preflight, protected backup, rollback boundary, one-business canary + canary tooling.
