## Runtime change (`index.html` only)
1. **HF-1 helper block** (`window.MarjinConfigMerge`, unchanged exports kept) gains:
   - `decodeRawBusinessConfigNode(raw)` — the exact raw-node table: `null`/`undefined` ⇒ confirmed absent (empty base); plain object without own `_v` ⇒ legacy direct config (all properties merged, normalised to `_v`); own `_v` string holding a JSON object ⇒ decoded, envelope siblings kept; array/primitive node, non-string `_v`, invalid JSON, JSON `null`/array/primitive ⇒ malformed.
   - `makeSetupWizardConfigTxn(intent)` — the PURE transaction callback: decode → the already-approved `mergeSetupWizardConfig` allowlist merge (11 keys + 3 `targets` sub-keys, unchanged) → `{...envelope, _v: json}`; malformed (or any thrown error) ⇒ `undefined` (abort). No I/O, UI, clock, randomness or logging; same input ⇒ same output.
   - `runSetupWizardEditSave(io, req)` — the orchestration: freezes `{tenantId, bizId, gen}` and the wizard intent / supplier / fixed payloads; derives every key once from `ctx.bizId`; order **config transaction → `app-businesses` → suppliers → fixed (if any)**; `live()` = `selection.isLive(ctx) && isCurrentOp(token)` checked immediately before every dispatch and immediately after every await; stops at the first failure or stale boundary; only `committed === true` counts; the committed config is decoded from the transaction's result snapshot; the business list's name comes from that committed config; returns `committed` / `stale` / `failed` with a typed `stage` + `reason` (`permission_denied`, `retry_exhausted`, `write_failed`, `not_committed`, `malformed_config`, `commit_unreadable`, `missing_identity`, `wizard_malformed`; the call site maps an unexpected exception to `unexpected_error`). No outer retry, no rollback.
2. **Edit-mode `<SetupWizard onComplete>`** — captures the selection, takes a fresh per-submission operation token (`setupEditOpRef`, new `useRef`), rejects a context that is not live or does not match `currentBizId`, and calls `runSetupWizardEditSave` with `window.storage.mutateFor` (config) and `window.storage.setFor(…, true)` (later writes) — both explicit-tenant. The mutable-tenant `window.storage.get` / `set` are no longer used on this path. Local state (`setBusinessConfig`, `setBusinesses`, `setSuppliers`, `setFixedList`, `setShowSetup(false)`, `setSetupDone(true)`) is applied **only** after the full sequence commits and the context and token are still current. `stale` ⇒ silent no-op. Failure ⇒ the wizard stays open with a Hebrew message (malformed stored config: the existing "not saved to protect existing data" message; otherwise "save not completed — not fully saved, try again"); the console gets only the stage and typed reason.
3. `const setupEditOpRef = useRef(null);` next to the other selection-bound refs.

Unchanged (byte-identical, test R1-27): `completeSetup`, the create-new-business `<SetupWizard>` call site, `SetupWizard` / `finish`, `saveBusinessConfig` and the Employees / petty-cash writers, the storage layer (`mutateFor` / `setFor` already existed), Rules.

## Semantics (contract 01–03)
- Concurrent non-owned changes (employees, petty-cash, unknown / nested / future keys, unknown `targets` sub-keys) survive: RTDB compare-and-swap reruns the callback on the fresher value (Firebase JS 10.7.1, bounded at 25 attempts).
- A concurrent change of a wizard-owned key: the wizard's submitted value wins at its successful commit (documented deterministic policy).
- An in-flight write cannot be cancelled; it can only settle at the captured explicit destination. Nothing after it is dispatched; no UI change.
- Residual (disclosed, contract 03): after the config commit a later write can fail ⇒ a visible partial save; the wizard stays open; the idempotent retry converges (R1-25). The `app-businesses` whole-list write keeps its pre-existing multi-writer lost-update exposure (out of HF-1 scope). A duplicate submission's older in-flight config transaction may still settle (same captured node) after the newer one; with a duplicate click the intents are identical, and only the current operation owns later writes / UI (R1-26).
