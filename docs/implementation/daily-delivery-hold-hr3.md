# HR3 local implementation — incomplete; not ready for independent acceptance

Owner decision, 2026-10-15: an exact durable date inventory is bound to the hold generation; operator verification of complete coverage is required before release. A declaration alone cannot prove coverage. Uncertain dates stay blocked, and are not labelled as proven refused. No blanket release-date fence or manual catch-up permission was approved.

The local prototype writes an intent under the hold node before reading the hold. A completed refusal records its exact business date and intent; a failed finalization or abandoned process leaves pending evidence. Hold generation changes invalidate operator review; inventory changes increment revision and invalidate review. The review digest includes sorted complete entries, refusal proofs, generation, revision, state/version and the full hold audit. Confirmation is a record of review only.

Release currently has NO success path. Missing, malformed, unreadable or incomplete inventory refuses. Even an exact operator review returns `inventory_coverage_unverified` on release. The component has no independent authoritative durable ingress inventory against which to verify completeness after the FIRST intent write fails and the process disappears. Empty database trees, operator declarations, logs-attested flags and stopped cron cannot distinguish this from an invocation that never existed. No implementation of a verifier is invented here. No flag or confirmation clears this block.

This is a precise remaining HR2-R-01 limitation, not a completed release protocol. A trusted pre-existing invocation/admission inventory or equivalent independently verifiable basis is needed before adding a release-success path; adopting that dependency requires a separate bounded design/review. No operator is assigned by this document.

Pending intents are retained through generation changes. They have no timeout-based repair or manual deletion interface. An unchanged valid released audit/version proves no intervening hold since admission, so concurrent intents from that exact version can be resolved as allowed. Intents from any earlier version remain uncertain. This narrow audit fact is not a proof of full invocation coverage. Existing HR1/HR2 assertions remain intact and expose contract/availability failures; do not hide them or call the candidate ready.

Legacy HR1 release records carry no HR2 fence. HR2 records carried a broad fence; HR3 does not use it as a range and does not infer its missing exact dates. Previously lost evidence cannot be reconstructed. A legacy HR2 range without exact evidence is retained as `legacyUncertainThrough` and blocks affected dates as unverifiable, not as proven refused. Admission and generation changes preserve it; its value is included in the review digest. Fresh HR3 generations do not create a clock-derived range. A bootstrap must stay held until supported completeness evidence is available. A hold/release cycle alone is insufficient under this incomplete HR3 protocol. Re-init still digests malformed prior state (existing E1 retention limitation); it never establishes completeness.

Receipt/claim/provider/manual-send state machines, unknown outcomes and budgets are unchanged. An admitted hand-off after an open final read cannot be cancelled by a later hold. Missing receipts, empty trees or cron status never establish drain. Operational R2/R3, named operators, P7, integration and all hosted/release gates remain open. No live operation is authorized here.
